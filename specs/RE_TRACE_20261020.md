### Native dispatch and final damage stages

Saved `SkillActionBase.CalcDamage` calls temporary skill-buffer activation,
dispatches through the concrete action's virtual entry at class `+0x4a8`, then
invalidates temporary buffers. See
`%TEMP%/combat-decompile-2260/callback-decompiled/SkillActionBase.CalcDamage.7ffba69b68f0.c:143`
and `:162`. The exported base `SkillActionBase.calcPlayerToMobDamage` is a

The saved symbols do not identify the concrete Hard Hit native method.

Five additional functions were decompiled from the existing snapshot:
`PlayerAttackBase.CalcLastDamageRate`, both `templateToDamageData` overloads,
`SkillActionBase.CalcActualDamage`, and `SkillActionBase.CalcMultiDamage`.
New C output stays outside the repository in
`%TEMP%/combat-decompile-2260/skill-review-decompiled/`.

Verified control flow adds useful distinctions:

- `templateToDamageData.7ffba656ef30.c:51` tests a template result flag before
  populating damage/count/hit fields; the other branch sets count and hit
  fields to zero and constructs a different current-damage record (`:78`).
  This is a local classification branch, not evidence of remote rejection.
- `CalcActualDamage.7ffba69b66c0.c:38` consults the per-target limit map and
  can return zero (`:44`). Its later branches apply additional target-state
  limits. The map at action `+0x68` is independently corroborated by the
  current exported `get_TargetMobDamageLimitList` getter.
- `CalcMultiDamage.7ffba69b72f0.c` applies a conditional per-target repeated-hit
  adjustment and writes resulting damage fields. This is not established as
  the ordinary three-category proration mechanism.

These are candidate observation points, not explanations proved for damage IDs
37/39. The capture has no template flags, concrete skill calculation, target
limit-map state, or final local per-hit amount for those actions.

Decompiler signatures also need care: the existing symbol-export schema loses
by-reference primitive information. Older `CheckDamageLimit`/`GetLimitDamage`
output consequently renders out-parameter addresses as scalar `int`/`bool`
arguments. Use native pointer operations and verified signatures before using
that output to implement a callback. No native ABI changes were made here.

## 2. MP: bonus nonexecution and settlement are different facts

The hit callback at `crates/wcore/src/features.rs:1260` forwards native work and
samples MP. It does not add MP. The bonus getter increments its invocation
counter at `:1384`, before ownership and bonus checks. The saved session's
zero getter counter therefore supplies no evidence that an added +50 was
applied and rejected.

Installed detour pointers are present in the saved MethodInfo descriptors at
`work/gameplay-20261020-16932/native-inventory.log:23` and `:26`. However,
`crates/wcore/src/hook.rs:307` changes MethodInfo pointers and a matching vtable
slot; it does not intercept compiled direct calls or every derived dispatch
table. The precise statement is **no completed intercepted getter calls were
observed**. No direct AMPR caller was identified in the limited saved exports;
direct-call paths, caching, and another calculator remain unverified.

The native settlement chain is:

`GameManager.UpdatePlayerStatusFromDamage`
→ `PlayerDataManager.UpdateServerMp`
→ `MainPlayer.UpdateServerMp`
→ `PlayerGameStatus.SetMp`.

The current `SetMp` assembly writes the received value into both `serverMp`
and `localMp` (`+0x18` and `+0x1c`), and likewise updates the extra-MP pair.
This explains why a direct local bar fill is replaced on settlement. It does
not reveal the remote recovery formula.

Exact external evidence:

## 3. Range: gate, movement radius, and initialization are distinct

Saved `BattleManagerBase.actionReserve` stores the pending action, then invokes
slot 17 `CheckActionRange`, selecting the out-of-range or in-range path before
the later attack preparation. `ActionUpdate` repeats the gate.

`PlayerBattleManager.checkAssistMove` separately reads action range at `+0x20`,
adds target size, and supplies the radius to movement before setting
`IsAssistMove`. `OnActionRange` clears the state and performs movement cleanup.
`NormalAttackAction.OnInitialize` also calls `GetWeaponRange` and writes the
backing range, with further writes in additional branches.

Strongest native references under `%TEMP%/combat-decompile-2260/`:

- `consistency-decompiled/BattleManagerBase.actionReserve.7ffba689ae80.c:228`
- `consistency-decompiled/PlayerBattleManager.checkAssistMove.7ffba652c6e0.c:168`
- `decompiled/NormalAttackAction.OnInitialize.7ffba6550df0.c:57`

The failing installed snapshot's hook log
(`work/gameplay-20261020-16932/comparison-session.log:76`) lacks a pending-gate
hook; `work/consistency-20261020/current-range-slot.json` records slot 17 still
pointing to native code. The dirty source already contains a different
three-hook candidate at `crates/wcore/src/features.rs:2589`, including a
vtable-only pending-range override. Its presence in source does not prove it
was installed in that capture.

The saved code establishes possible reset/order mechanisms, but it does not
show the failing action's actual range before the gate or when initialization
ran. A separate movement-state check can also select the out-of-range branch.

The existing geometry evidence maps raw distance through
`ceil(adjustedDistance * 0.5)`. Thus raw range 30 is approximately 15 HUD metres,
not the menu's 30m. That mismatch alone does not explain approaching to native
sword reach. Details and references are in
`work/re-review-range-20261020.md`.
